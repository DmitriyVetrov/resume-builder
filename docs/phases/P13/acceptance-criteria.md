# P13 Acceptance Criteria

Observable criteria. Every Must has a positive and a negative case in the test plan. "Real stack" means the built frontend, the API in `Production`, Mongo and Azurite from Compose, as in P11 and P12.

| ID | Pri | Source | Pass when |
|---|---|---|---|
| AC-P13-01 | M | FR-LIB-04, ADR-016, ADR-039 §3 | A trashed resume whose `purgeAt` has passed is purged by the trash-expiry job: its `resume` and `photo` ledger entries are in both the collection and the blob container before the resume, its snapshots and its photo blobs are gone. A resume restored before the run, one still inside 30 days, and another owner's resumes are untouched. A failing resume does not stop the others; a second run is harmless; a pending count is logged without IDs. |
| AC-P13-02 | M | ADR-007 | Each scheduled job (account purge, resume lifecycle, trash expiry) runs under a lease: two workers with the same lease run a period's job once; after the lease expires another holder takes it over. |
| AC-P13-03 | M | FR-ACC-03, ADR-039 §2 | An account with active and trashed resumes, photos (one pending removal), snapshots and idempotency records, deleted through the API with re-authentication, is gone from every live collection and blob prefix after the job runs at +24 h, and its `account` entry is in both ledger stores. Another account is untouched. Before +24 h login is already refused. |
| AC-P13-04 | M | ADR-039 §4, DD-P13-04, DD-P13-05 | `reconcile-restore` runs steps 1–6 in order and reports counts only. It loads ledger entries from the blob copy into a restored collection that lacks them. Running it again changes nothing. It starts no hosted worker and no HTTP listener. |
| AC-P13-05 | M | NFR-10, T-ID-09 | The drill takes a database dump and a photo-container copy, then performs: an account erasure, a "Delete permanently" from the trash before 30 days, a purge by the job, a photo removal and a photo replacement. After restoring both and reconciling, each of the five stays gone (rows and blobs), the restored resume no longer references the removed photo, and expired snapshots and orphan blobs are gone. A trashed resume with a photo and an active resume with a photo keep their blobs. |
| AC-P13-06 | M | NFR-10, ADR-037 | In a journey covering every write path, every write command reaching Mongo carries `w: majority` or none, and the cluster's default write concern is majority. The runbook states continuous backup with point-in-time restore (RPO ≤ 1 min), daily snapshots kept 30 days, and blob point-in-time restore, all in the EU, for P15. |
| AC-P13-07 | M | NFR-08 | Every operation in the contract is classified (public, session or owner-scoped). Anonymous callers get 401 on every non-public operation; another user's IDs get 404 on every owner-scoped one and change nothing; an account pending deletion has no working session. An operation added to the contract without a classification fails the test. |
| AC-P13-08 | M | NFR-08, T-TA-04, T-ID-04, T-DS-03 | A PNG and a JPEG whose headers claim 65 000 × 65 000 px in a small file, a truncated image, an SVG and an HTML file sent as `image/png`, and an empty file are refused with the contract's codes within 2 s each, and nothing is stored. GPS metadata never reaches master or rendition. |
| AC-P13-09 | M | NFR-13, T-ID-05 | A canary journey (sign-up, verification, login, reset, re-auth, resume create, document writes, photo upload, snapshot, trash, restore, purge, data export, client events, account deletion, every job, reconciliation) captured at Trace level for every category leaves none of its canary strings (e-mail, password, tokens, resume text, file names, photo bytes marker) in any log message, state value or exception. |
| AC-P13-10 | S | NFR-13, ADR-034 | Under the production log filters, `account_mail_delivery_failed`, `account_purge_pending`, `resume_lifecycle_pending`, `trash_expiry_pending` and the reconciliation summary are emitted with counts only; framework categories stay silent. |
| AC-P13-11 | M | NFR-08, NFR-09 | The API sends `Strict-Transport-Security` in Production and not in Testing. The web image sends the CSP of DD-P13-18, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, a restrictive `Permissions-Policy` and HSTS; hashed assets are `immutable` for a year and `index.html` is `no-cache`. The fixture E2E suite runs under the same CSP in Chromium, Firefox and WebKit with no violation. |
| AC-P13-12 | S | P04 i-2 | `X-Forwarded-For` and `X-Forwarded-Proto` from an address inside a configured trusted network are applied; from outside it they are ignored. |
| AC-P13-13 | M | P10 carry-in | The race is reproduced deterministically before the fix. After it, concurrent session bootstraps and a mutation never surface `csrf_token_invalid` to the user, and a fresh host answers concurrent first requests without a 403. A forged request without the token is still 403. |
| AC-P13-14 | S | FR-ACC-04, ADR-039 §6, DD-P01-36 | After re-authentication, one click downloads one ZIP that an independent reader accepts, holding `account-data.json`, `manifest.json`, and per resume (active and trashed) the photo master, the PDF and the TXT of the current version. The PDF equals the one-click export of that version. Progress shows "n of N"; Cancel downloads nothing; a failing PDF is listed in the manifest and the rest is delivered. A nameless resume has no PDF or TXT and is listed as `no_full_name`. Unverified accounts cannot start it. |
| AC-P13-15 | M | NFR-10, ADR-037, ADR-029 | Against the real API: a document write whose response is lost after the server applied it is retried with the same key and shows Saved with no conflict and one version step; a burst of 503 answers keeps the edits locally and saves after recovery. With Mongo paused, readiness is 503 and a write is never acknowledged; after resume the same keyed write applies once. |
| AC-P13-16 | M | NFR-09, D-20, ADR-012 | No browser request leaves the origin in the fixture suite and under the CSP; the backend has no outbound HTTP client (architecture test); the runbook has a residency check per store. Production evidence is assigned to P15. |
| AC-P13-17 | M | ADR-039 §4, ADR-036, ADR-012 | `docs/operations/runbook.md` holds: restore (database, blobs) followed by `reconcile-restore` with traffic off; data-protection key rotation; residency checks; backup policy and log retention values; job and lease behaviour; the effective rate limits. |
| AC-P13-18 | M | NFR-06, FR-EDT-07, §3.2 | The archive controls are keyboard reachable, progress is announced in a status region, axe finds no violation, nothing overflows at 390 px, in light and dark. Nothing from TECHNICAL-SPEC §3.2 is built; no e-mail or share of the archive. |
