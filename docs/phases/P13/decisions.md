# P13 Decisions

All entries are decided by the operator under delegation (ADR-051 S-5), 2026-11-12, and tagged `DELEGATED-DEFAULT`. No register row is `OPEN` or `SOURCE-OPEN` for this phase.

| ID | Question and options | Decision and reason | Source |
|---|---|---|---|
| DD-P13-01 (`DELEGATED-DEFAULT`) | Does P13 change the contract? Options: (a) a server-built ZIP endpoint, (b) an admin endpoint for reconciliation, (c) no change. | **(c).** ADR-039 §6 and ADR-010 §5 put the archive in the browser, and `exportAccountData`, `getPhotoMaster` and `getPhotoRendition` already serve every byte it needs, trashed resumes included (P07 P06 test). Reconciliation is an operator action with traffic off, not an API. Step 2 is skipped. | ADR-039 §6, ADR-010 §5, ADR-006 |
| DD-P13-02 (`DELEGATED-DEFAULT`) | How does the hourly trash purge delete? Options: (a) a bulk delete by `purgeAt`, (b) the two-phase purge of DD-P07-10 per resume. | **(b).** It reuses the ledger-first `FinishPurgeAsync`, so the `resume` and `photo` entries reach both stores before anything goes, and a crash is finished by the lifecycle worker. The first phase is a conditional replace on the read version with a fresh key, so a restore that lands first wins and the resume is skipped. Bulk delete would skip the ledger (ADR-039 §3). | ADR-016, ADR-039 §3, DD-P07-03, DD-P07-10 |
| DD-P13-03 (`DELEGATED-DEFAULT`) | ADR-007's lease-based job runner. Options: (a) none, rely on idempotency, (b) a Mongo lease per job name, (c) a library (Quartz, Hangfire). | **(b).** Every job is already idempotent, so correctness does not depend on it, but N replicas would each run each period. One `findOneAndUpdate` on `job_leases` with the lease lasting one period gives one run per period across replicas, needs no new dependency and runs on the store we have. The lease is not released after a run: releasing would let another replica run the same period again at once. A crashed holder loses the lease at expiry. | ADR-007 Consequences, ADR-042 |
| DD-P13-04 (`DELEGATED-DEFAULT`) | Entry point for restore reconciliation. Options: (a) an admin HTTP endpoint, (b) a separate console project, (c) a `reconcile-restore` argument to the API binary. | **(c).** The same image and wiring as production, no new attack surface and no contract change. In this mode the host is built, the reconciliation runs, a counts-only summary is logged, the exit code is 0 or 1, and `app.Run()` is never reached, so hosted workers and Kestrel never start. The runbook runs it as a one-off job with ingress off. (a) adds an endpoint that can delete across accounts; (b) duplicates the wiring. Recorded in the ADR-039 P13 amendment. | ADR-039 §4, ADR-033 |
| DD-P13-05 (`DELEGATED-DEFAULT`) | P01 m-10: what is "live" in the orphan sweep, and what of photos pending removal? | **Any resume document present in the restored database, active or trashed; a photo ID in `photo` or in `pendingPhotoRemovals` is referenced.** Trashed resumes can still be restored for 30 days and must keep their photos. Pending removals are finished by the lifecycle worker, which writes their `photo` ledger entries; deleting them in the sweep would skip that. The drill has a trashed resume with a photo. Recorded in the ADR-039 P13 amendment. | ADR-039 §4 step 6, P01 review m-10 |
| DD-P13-06 (`DELEGATED-DEFAULT`) | Reconciliation step 4 must "clear `header.photo`" in a restored resume. How? | **Set the aggregate's `photo` to null and increment the version, conditional on the photo ID**, without a `LastOperation` or a pending removal: the blobs are already gone. The `photo` lives on the aggregate, not in the document header. A tab holding the old version gets 412 and follows ADR-029, which is right after a restore. | ADR-039 §4 step 4, ADR-037 |
| DD-P13-07 (`DELEGATED-DEFAULT`) | How does the automated drill restore? Options: (a) copy collections in the test, (b) `mongodump`/`mongorestore` of the database plus a blob container copy, (c) a cloud PITR. | **(b),** inside the test's Mongo container, with the photo container copied to memory and re-uploaded, and the `deletion-ledger` container left out of the restore as ADR-039 §4 requires. (c) needs an Atlas account (P15). The production mechanics differ, the reconciliation is identical, and the runbook names both. | NFR-10, ADR-039 §4, ADR-004 |
| DD-P13-08 (`DELEGATED-DEFAULT`) | NFR-10 "RPO ≤ 1 min; daily backups kept 30 days". What can P13 prove locally? | **The application half:** a profiler-level test asserts that every write command in a full journey carries `w: majority` or inherits a cluster default of majority, so an acknowledged edit is never one a failover can roll back. **The backup half** (Atlas continuous cloud backup with point-in-time restore inside 1 min, daily snapshots kept 30 days, Blob point-in-time restore and soft delete for 30 days, EU regions) is specified in the runbook for P15 to apply and verify. | NFR-10, ADR-037 §5, ADR-004 |
| DD-P13-09 (`DELEGATED-DEFAULT`) | P01 review m-7: retention of accounts that never verify. Options: (a) expire after N days without verification and activity, with a notice, (b) explicit acceptance. | **(b), no automatic expiry in v1.** ADR-013 lets an unverified user log in and write resumes, so expiry would delete user content on a timer; the user can delete the account at any time (FR-ACC-03), and sign-up is rate-limited (ADR-038). The privacy notice (P15) states it. Revisit at P15 if sign-up abuse shows in the counters. | P01 review m-7, ADR-013, ADR-038, NFR-09 |
| DD-P13-10 (`DELEGATED-DEFAULT`) | P06 review m-3: in-process rate counters are per replica. | **Kept per replica in P13.** Per-address e-mail and login back-off are already in Mongo, which are the abuse-relevant ones. The fixed-window IP limits become N × limit with N replicas; P15 sets the replica count and decides whether to share them. The runbook records the effective limit. | ADR-038, P06 qa-report |
| DD-P13-11 (`DELEGATED-DEFAULT`) | Archive format and library. Options: (a) add `fflate` or `jszip`, (b) an in-repo store-only ZIP writer. | **(b).** PDFs, JPEG and PNG are compressed already, so deflate would save little; a store-only writer is about 80 lines with CRC-32, and adds nothing to the supply chain (ADR-042). It is verified by an independent reader: Node's `zlib.crc32` in tests and `unzip -t` at acceptance. The 200-resume worst case (≈ 1.2 GB) stays under the 4 GB and 65 535-entry limits, so no ZIP64. | ADR-042, ADR-039 §6 |
| DD-P13-12 (`DELEGATED-DEFAULT`) | Archive layout. | `resumiser-data-<YYYY-MM-DD>.zip` with `account-data.json` (the API response as received: the same JSON value, written indented; byte equality with the response is a review follow-up, `review/code-review.md`), `manifest.json`, and per resume `resumes/<resumeId>/` holding `<exportFileName>.pdf`, `<exportFileName>.txt` and `photo-master.<jpg|png|webp>`. The folder is the ID, so two resumes with one title cannot collide. The manifest lists every resume with its state, files and missing files with a reason code. | FR-ACC-04, FR-PDF-06 |
| DD-P13-13 (`DELEGATED-DEFAULT`) | ADR-039 §6 "batches with progress and cancel; the PDF part may be partial". | **One resume at a time**, progress "n of N" after each, Cancel aborts the in-flight fetches and drops the parts, and nothing downloads after a cancel. A failed PDF, TXT or photo is listed as missing and the archive goes on; only a failed JSON read fails the whole archive, because there is nothing to archive without it. | ADR-039 §6, DD-P01-36 |
| DD-P13-14 (`DELEGATED-DEFAULT`) | FR-TYP-03 says a resume needs a full name to export. A nameless resume in the archive? | **No PDF or TXT; the manifest lists both as `no_full_name`.** Its data is in `account-data.json` anyway. This keeps one export rule. | FR-TYP-03 |
| DD-P13-15 (`DELEGATED-DEFAULT`) | Unverified address and the archive. | Unchanged from P06: the button is disabled with its reason, and the server answers 403 `email_not_verified` (ADR-013). | ADR-013, AC-P06-08 |
| DD-P13-16 (`DELEGATED-DEFAULT`) | Does the archive take a `before_export` snapshot per resume, as one-click export does (DD-P12-11)? | **No.** The archive is a copy of the account's data, not an export of one resume; 200 snapshot writes would be noise in each history and a write inside a read. The bytes still equal a one-click export of the same version (ADR-010 §7). | FR-PER-05, DD-P12-11 |
| DD-P13-17 (`DELEGATED-DEFAULT`) | The cold-start 403 (P10). Options: (a) leave it, (b) single-flight the CSRF bootstrap, (c) (b) plus one automatic retry after `csrf_token_invalid`. | **Decided at step 4 from the red evidence; the plan is (c).** The client reads the CSRF header from `document.cookie` before `fetch`, so a late `GET /session` response can replace the cookie pair under an in-flight mutation. Antiforgery runs before any effect, so a mutation rejected with `csrf_token_invalid` changed nothing and one retry with a refreshed pair is safe. This revises the P06 choice to leave the retry to the user. | P10 qa-report, ADR-036 |
| DD-P13-18 (`DELEGATED-DEFAULT`) | Content-Security-Policy and how to test it. | `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' blob: data:; font-src 'self' data:; connect-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`. `'unsafe-inline'` for styles only, because Radix injects style elements; scripts stay `'self'` and the build has no `eval`. `connect-src 'self'` makes NFR-09's "no third-party trackers" structural. The web image's nginx serves it, and `vite preview` serves the same string through `preview.headers`, so every fixture E2E test in three browsers runs under it. Dev (`vite`) is unaffected. | NFR-08, NFR-09, ADR-042 |
| DD-P13-19 (`DELEGATED-DEFAULT`) | NFR-08 "HTTPS only" in the application. Options: (a) `UseHttpsRedirection` in the API, (b) HSTS and secure cookies in the app, redirect at the ingress. | **(b).** TLS ends at the Container Apps ingress, which redirects HTTP (P15, `allowInsecure: false`). The API sends HSTS in Production; the web image sends HSTS; `__Host-` cookies are `Secure` already, so no session travels over HTTP. (a) would loop behind a proxy that forwards plain HTTP. | NFR-08, ADR-033, ADR-036 |
| DD-P13-20 (`DELEGATED-DEFAULT`) | P04 i-2: the ingress needs network ranges. | `ReverseProxy:TrustedNetworks` takes CIDR entries beside `TrustedProxies`; unparsable entries are ignored, as before. | P04 review i-2, ADR-033 |
| DD-P13-21 (`DELEGATED-DEFAULT`) | The production log floor is `None` with three categories re-enabled, so `account_mail_delivery_failed` never reaches a log. | **Re-enable at `Warning` the Infrastructure categories that emit counts-only events** (`AccountEmailDispatcher`, the job worker, `TrashExpiryJob`), and at `Information` the reconciliation summary. Each of these messages is a `LoggerMessage` with counts only. Framework categories stay silent (P04 C-1). | NFR-13, ADR-034, P04 review C-1 |
