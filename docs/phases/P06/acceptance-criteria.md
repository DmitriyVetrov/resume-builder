# P06 Acceptance Criteria

The Test Architect maps each criterion to executable cases within the kickoff budget. Every Must criterion has a positive and a negative case; the named negatives below are mandatory. P06 verifies the account slice available before P07/P08/P12/P13 and records those handoffs without claiming the later complete archive or guest flow has passed.

| ID | Priority / source | Observable pass criteria (positive and negative) |
|---|---|---|
| AC-P06-01 | Must; FR-ACC-01 | New syntactically valid email/password sign-up returns 202, creates one unverified account, queues a verification email and opens no session. Repeating it or using an already registered address still returns the same 202 and does not create another account or disclose existence. Passwords outside 10–128 code points or on the common list return contract password validation codes without echoing input. |
| AC-P06-02 | Must; FR-ACC-01, D-01 | A single-use verification token delivered through the local email sink verifies the account within 24 h and `GET /session` then reports `emailVerified: true`. Invalid, expired, reused and superseded tokens return 400 `token_invalid` without changing an account; resend is generic 202. |
| AC-P06-03 | Must; FR-ACC-01/02, ADR-013/036 | An unverified account can log in, receives a rotated opaque secure cookie, can retrieve its own session and can log out; a subsequent protected request is 401. Unknown address, wrong password and backed-off login share generic failure semantics, while unverified account data export is 403 `email_not_verified`. Anonymous `GET /session` remains 200 with `authenticated: false`. |
| AC-P06-04 | Must; FR-ACC-02 | Password reset request sends a one-hour token through the local sink and answers generic 202. Valid confirm changes the password, verifies email and revokes every session; wrong/expired/reused/superseded tokens return `token_invalid`, and old credentials/sessions fail. Sign-up/reset-request/resend responses do not reveal whether an address exists. |
| AC-P06-05 | Must; FR-ACC-02, NFR-08 | A current session can re-authenticate with its password; within five minutes `changePassword` succeeds, clears its cookie and revokes all sessions. Wrong password returns 403 `reauthentication_failed`; missing/stale re-auth returns 401 `reauthentication_required`; old sessions remain unusable. |
| AC-P06-06 | Must; NFR-08/09, ADR-036/038 | A bootstrapped CSRF token permits unsafe auth/account requests; missing/wrong token returns 403 even on anonymous POSTs. Cookie attributes, no-store on session/export, 429 with `Retry-After`, password-hash algorithm/iteration setting, token-hash-only persistence, constant-time token verification and safe error envelope are verified by focused tests. No password, token, address, cookie, resume content or archive bytes appear in captured application logs. |
| AC-P06-07 | Must; FR-ACC-03, NFR-09/10, ADR-039 | With fresh re-auth and explicit UI confirmation, deletion returns 202, disables login and revokes all sessions immediately. A controlled clock/job run shows P06-owned account, token, session and outbox data purged within 24 h, with both Mongo and private Blob ledger entries durable before any destructive operation. Missing/stale re-auth or failed ledger write prevents deletion; a restarted job resumes without loss or duplicate harm. P07/P13 aggregate data/restore obligations remain named in the gate report. |
| AC-P06-08 | Should, privacy risk; FR-ACC-04 | A verified, freshly re-authenticated account receives one `AccountDataExport` JSON response containing only its own account fields and the contracted empty-resume list in P06, with `Cache-Control: no-store`; the UI identifies this as JSON. Anonymous, unverified or stale re-auth callers fail with the contract's 401/403; another user's account data never appears. Full ZIP/PDF/TXT/photo acceptance is assigned to P13. |
| AC-P06-09 | Must; NFR-08/09/12, P02 contract | All twelve P06 operations have exact `/api/v1` paths, methods, statuses, response media, Problem codes and security metadata from OpenAPI 1.0.0. Authentication is checked before owner-scoped account reads, and non-owner data is absent. Invalid media/body and rate-limit branches use contracted errors; no extra auth/Google/guest/export endpoint exists. |
| AC-P06-10 | Must UX for account flows; FR-ACC-01/02/03, NFR-05/06; Could FR-ACC-06 seam | Sign-up, verify, login, reset, logout, re-auth, deletion confirmation and JSON download are reachable by keyboard at 390 px without horizontal page overflow; forms have labels, status and recoverable errors. The claim prompt component, when given a draft summary, requires an explicit Save or Discard choice and cannot silently upload; P08 supplies a real draft and performs claim. A no-draft state shows no misleading claim action. |
| AC-P06-11 | Could deferred; FR-ACC-05, D-02 | No Google sign-in control, external identity dependency or OAuth endpoint is added. The P06 report records ADR-014 and the later scope. |
| AC-P06-12 | Must P06 visual delivery; owner UI/UX direction, FR-ACC-01/02/03, NFR-05/06 | Rendered sign-up, login, verification, reset and account settings match the hierarchy, token roles, spacing, form grouping and action priority in `architecture/ui-ux-design.md` at 1280 px and 390 px. At 1024 px the layout switches without clipped fields or unexpected horizontal scrolling; at 200% zoom all account controls remain reachable and readable. Positive evidence: local synthetic-state screenshots for login idle/error, verification success/failure, settings and deletion dialog at desktop and phone, reviewed against the P06 design. Negative checks: no source wizard, score, publish, import, paywall, external font/tracker or misleading final-archive control appears. Source screenshots are references, not pixel-equality baselines. |
| AC-P06-13 | Must accessibility/recovery; NFR-06, owner UI/UX direction | All P06 forms and dialogs have programmatic names, visible focus, 4.5:1 normal-text contrast and 3:1 focus/UI contrast on their actual surfaces, and announce validation/status without color alone. Keyboard-only users can complete login, reset, JSON download and cancel/confirm deletion; dialog focus stays inside and returns to its trigger on cancel, with no hidden destructive default. At `prefers-reduced-motion: reduce`, nonessential transitions/translation are absent. Positive and negative accessibility checks plus manual keyboard, focus and 200% zoom observations are recorded by QA; an automated axe pass alone is insufficient. |

## Evidence and gate

Test Engineer records red harness proof and exact commands/exits in `tests/test-results.md`; developers append green command evidence; QA reports the integrated positive/negative E2E and security checks. No failing Must test, unresolved privacy/security blocker, contract drift or unapproved path change can pass the P06 gate. FR-ACC-03's full cross-store purge and FR-ACC-04's one archive remain release requirements for P13; P06's narrower positive fixtures are not their final acceptance.
